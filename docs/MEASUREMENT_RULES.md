# Measurement rules

SAQEF is a pre-registered measurement study. Its results are only as good as the discipline below.
Each rule was added after a measurement night was lost without it.

## Where things are
- `NEXT_STEPS.md`: what is still to run or do. Kept current.
- `TROUBLESHOOTING_RUNBOOK.md`: bug ledger, every pre-registration and every outcome. Start at its
  "Index: symptom → section" table. Every new bug or gotcha gets a row there.
- Results file: `VERIFIED_RESULTS.md` in the results repository, generated by a script. There are no
  side tables anywhere else.
- Measurement nights: one command, `sudo bash tools/go.sh [--workload X | --arm Y]`; progress
  `sudo bash tools/go.sh --status`.
- `results/` is git-ignored here. Every session is backed up to the results repository.

## Before interpreting any run
1. Read the run's pre-registration (predictions and decision rules) in the runbook first. Judge against
   it, not against raw numbers. A failed prediction is a finding, never a reason to re-run.
2. Aggregate runs only through each leg's `acceptance.json` `usable_runs` (runbook §23, §28.7).
3. Recompute claims per usable run, not over the whole leg.
4. Before claiming a cause, test it on the legs already on disk. Propose a new experiment only if
   existing data cannot answer it (§28.9 B).
5. Current load: `/proc/stat` deltas or `pidstat`. Never `ps %CPU`, which is a lifetime average.
6. A comparison across sessions with n = 5 short runs cannot size a day-to-day shift. Prefer
   within-session A/B designs.
7. RAPL FIT warnings are expected (the 3.5 W per core model is retired, §25.1). Energy is RAPL,
   idle-probe basis.
8. Label OpenWhisk results "OpenWhisk standalone": its ~12 ms per invocation of child-process CPU is
   the standalone's `docker logs` log collector (§28.9 D). With it off (`SAQEF_OW_LOGSTORE=driver`,
   §29.1), OpenWhisk control-plane CPU falls from ~21 to ~3 ms per invocation and throughput rises
   from ~100 to ~305 rps, where its 2 action containers saturate (§29.2 D; the light platforms run
   16 replicas). Say both when comparing OpenWhisk throughput, latency or energy per invocation.
9. The quiet gate's floor is the stacks' own idle CPU (~7–8 % of 8 cores, §29.2 A). A gate failure
   right after a deploy is start-up noise, not an outside process. Read the gate's window process
   list (own vs reaped columns), never `ps`.
10. The laptop's firmware caps the CPU near its base clock on low battery or a charger that does not
    charge (§31.14). Pre-flight check 8 refuses to start a session then.

## Changing code
- Measurement-path code must be committed before a night; the pre-flight refuses a dirty tree.
- Run `python3 -m unittest discover -s tests -q` after any change to `tools/`, `platforms/`, `saqef`
  or `saqef_harness.py`. Dry run: `sudo bash tools/run_final.sh --dry-run [flags]`.
- A changed analysis tool must reproduce the committed outputs byte for byte before its new output
  is trusted.
- New behaviour that would change a closed session's gates goes behind a flag, default off.
- Pre-registered protocols are frozen: a gate never changes after that workload's data is seen.

## Writing results
- Lead with what the data shows, then the caveats. Mark post hoc analyses as post hoc.
- Name every quantity and its unit.
